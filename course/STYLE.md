# 写作与术语规范（所有章节必须遵守）

## 1. 称谓

| 用 | 不用 |
|---|---|
| **本实训** | ~~本书~~、~~本教材~~、~~全书~~ |
| 本实训的任务 / 本实训约定 / 本实训后面会…… | 本书的第一课 / 全书复用 |

原因：这是一套**实训（PBL 项目制实操）**，不是一本书。措辞要让人一眼知道"这是要动手做出成品的实训"。

## 2. 环境表述：本地 vs 云端 agent（web-cb）——**最重要的一条**

本实训的正式运行环境是**云端 agent（web-cb）**：它会按 PBL 项目的不同，在云端预先准备好
**MCP 服务、skill、托管平台，甚至基础代码仓库**。学员**不需要**自己安装/配置这些，
但**必须知道它们是什么、各自负责什么**——否则出问题时无法判断是谁的锅。

因此凡是涉及"环境"的内容，一律采用**双栏对照**：

```
🖥 本地路线（可选，进阶/离线）   —— 你需要自己做什么
🌩 云端 agent 环境（web-cb，默认）—— 开箱已有什么，你只需知道什么
```

**判定原则**：
1. 云端已经配好的东西 → 写"已预置，无需操作"，但仍要讲清原理与它在流水线的位置
2. 只有本地才需要手配的（如本机引擎路径）→ 明确标注"本地路线才需要"
3. 两边都会发生、但形式不同的（如跑测试）→ 给出两条命令或说明入口差异
4. 凡是"换机器就要改"的配置 → 说明它在云端由平台托管，本地才落 `.codebuddy/local/*.json`

**每章至少有一处 🌩 云端对照说明**（环境、工具、命令、构建、发布都可）。
建议在章节里固定使用一个小节标题：`### 🌩 在云端 agent（web-cb）里是什么样`。

## 3. 每章固定结构（四件套 + 教学提示）

```
目标（一句话，可验证）
→ 正文分节（含 🌩 云端对照）
→ 🤖 可复制的 Agent 提示词（必须带"约束条款"）
→ ✅ 验证命令（云端/本地各一条，若不同）
→ ⚠️ 常见坑速查表
→ 📝 作业（至少 1 条"故意制造失败"）
→ 🎓 教学提示（概念锚点 / 演示顺序 / 误解纠正 / 分层 / 批改要点）
→ 📹 录屏分镜（时间轴 + 画面 + 解说词）
→ 🖼 配图清单（标注自动生成 or 手动；名字必须来自 shots.json）
→ 🎥 直播片段脚本
→ ❓ FAQ
```

## 4. 可验证性

- 每个论断尽量能落到一条命令或一个文件；不写"理论上应该……"这种无法证伪的话
- 数字（断言条数、面数、体积）以**当前仓库真实值**为准，并注明"只看 failed=0，不记数字"
- 不写"大概/可能/应该是"当作结论；不确定的地方写成"待验证 / 见 Txx"

## 5. 图片与视频

- 每一张图必须有确定来源：自动截图（`course_capture.py`）或手绘 SVG
- 配图清单里的文件名**必须**在 `course/media/shots.json` 中声明（由 `course_check.py` 校验）
- 视频放到 `course/media/video/<章号>/` 即自动内嵌；未提供时保留"视频位"提示卡

## 6. 交付与同步

- Markdown 是设计稿，`course/site/*.html` 是成品
- 改完 md 必须跑 `python tools/course_build.py` 并同步提交 `course/site/`
- 提交前跑 `python tools/course_check.py` 体检

## 7. 语气

- 直接、具体、少形容词；先说"怎么验证"，再说"为什么"
- 允许提醒风险（"Agent 很擅长让测试变绿——包括把测试删掉"）
- 不吹嘘工具；遇到工具缺陷就写进"坑速查"（例如 fontTools 合并可变字体会报错）

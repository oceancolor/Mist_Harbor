## 0. 结论摘要（v0.2）

1. **v0.1 的一句关键论断说错了，在这里更正**：我说 Townscaper 靠"运行时按邻域生成几何"。作者本人的原话是——**"我用方块瓦片做出方形的拼图块，然后把它们稍微扭一下去贴合"**。也就是说它**既不**程序化生成，**也不**穷举所有组合，而是**手工做少量标准接口的拼图块，由算法选排**。
2. **真正负责"不露缝"的是 WFC（波函数坍缩），不是规则引擎也不是查表**。作者原话：*"我给它一堆拼图块，它负责用这些块拼出一个**没有任何缝隙**的连贯环境（前提是确实拼得出来）。"*
3. **它靠两件事压住资产爆炸**：一是**形变复用**（同一个 authored 件变形去贴不同形状的格子），二是**算法选排**（同样几个萝卜能填很多坑）。**两条都比"多做资产"便宜，但都不是免费的。**
4. **作者亲口承认的两个弱点，正好落在我们最难的两处**：
   - **支撑/细长构件 = WFC 最容易失败处**：*"主要出现在钢结构支撑上……你会看到没接好的、悬空的钢架"* → 我们的**下接**正踩这个雷
   - **每次改动要在整个连通域内重解**：*"改动会在整个连接区域内涟漪传播……建筑越大，放置到装饰完成的延迟越长"* → 我们有 **12000 格**上限，这条是硬成本
5. **好消息**：本项目已经有 seeds 可用——`seychelles-spec.md` 里的**楔石**已经带「**石缝 / 石顶语义位**」概念，这就是"槽位契约"的雏形。
6. **坏消息**：**stencil 开窗**（Townscaper 处理"装饰落在转角/边界"的做法）在本项目的 GL Compatibility / WebGL2 口径下**完全没核实过**，不能想当然。

### 2.2 真实管线（四步）

**第 1 步 · 不规则网格生成**（Stålberg 自述）
> ① 在一个六边形里生成一堆三角形 → ② 随机删掉三角形之间的边，凑成四边形 → ③ 全部细分，剩下的三角形也变成四边形 → ④ 跑几轮松弛算法

**关键点：结果必须是四边形**，因为 Marching Cubes 要求四边形。作者另一处说明：
> *"它（网格）到处都不规则，但**是四边形构成的**。这意味着我做内容时可以用方形瓦片，做出方形的拼图块，然后**稍微扭一下让它们贴合**。"*

**第 2 步 · Marching Cubes（非标准用法）**
不是用来提等值面的，而是**用来放置手建的模块件**——把 MC 的 256 个三角形 case 换成**手工模型**。

> 🆕 **v0.3 补：这套"枚举"到底有多大**（来源 C′ 组 `twopointfive`，🟡 中）
> 标准 MC 的 256 种角点占用情形按对称性归约后是 **15 种基本构型**（计二义性 23 种）。Townscaper **上下不对称**（有地板/天花板之分），归约后是 **51 种基本构型**；而实际只需 **18 个手工 mesh**，其余靠**旋转与镜像**cover（`rot[129,72,36]` / `mirror[33,24,132,66]`）。
> 🔴 **这正是"枚举"的证据，不是"程序生成"的证据**：构件是**有限的、手工的、可数的**。它之所以看起来不像枚举，是因为下面两步（WFC 选排 + 按格子扭曲）把组合数藏起来了。

**第 3 步 · WFC 接管选排（核心）**
> *"我把我那个（简单的）Marching Cubes 算法，用（复杂的）波函数坍缩算法改造了一下。"*

WFC 的作用正是**让玩家放下的块彼此严丝合缝**（fitting together seamlessly）——作者定义：
> *"这个算法能让玩家放下的块彼此**严丝合缝**。听起来简单，但形状一复杂、配置一多，其实相当难。"*

**第 4 步 · 形变贴合**
第三方复刻仓库（ⓘ **非作者方法**，见 §2.1）观察到：模块从 Blender 导入时**按"邻格空/满 case"打标签**，但因为格子不规则**不能直接用**，要经**cage 形变**（球坐标均值坐标）去贴合。这与作者"skew 一下"的说法一致。

### 2.3 ⛔ v0.1 的错误（已作废 · 勿用 · 勿删）

> v0.1 §2 原文称："Townscaper 的'自动处理衔接'**不是靠一套庞大的资产库**，而是靠**几何在运行时按邻域生成**。"
>
> 🔴 **此判断已作废**。正确表述：**它是靠"少量手工制作的标准化拼图块 + 算法选排 + 形变贴合"**。这个更正很重要——如果照 v0.1 的错误理解去做，会往"全程序化生成"（路线 B）走，而那既不是 Townscaper 的做法，也不适合本项目的 Mesh / Blender 管线与面数预算。

### 2.4 v0.1 漏掉的四条机制

| 机制 | 出处 | 对我们的意义 |
|---|---|---|
| **WFC 会静默失败**，且**失败最明显处是支撑构件** | Thompson 访谈引述：*"Townscaper 里算法允许静默失败……主要出现在**钢结构支撑**上，那类细长的东西 WFC 不太擅长，你会看到没接好的悬空钢架"* | 🔴 **下接功能正踩作者承认的雷**。必须有兜底：解不出来时要么显式禁止放置，要么给出可接受的降级形态，**不能留悬空残件** |
| **代价随连通域增长** | 同上：*"一处改动会涟漪传播到整个连接区域，WFC 要重新确认所有约束……建筑越大，延迟越长"* | 🔴 我们有 **12000 格**上限 + 每次放置全量重建。**若引入 WFC，必须先做局部性治理**（分区传播 / 坍缩半径上限），否则 Web 端必炸 |
| **装饰物不建模进瓦片里，用 stencil buffer 切出来** | 同上：窗户是*"网格放好后用 stencil buffer 切出来的，而不是做进瓦片里——否则边界情况太多，会出现切一半、卡在转角上的窗"* | 💡 **这是"装饰落在转角/边界"的标准解法**。但要核实 Compatibility/WebGL2 支持（§6 R-1） |
| **规则写在"块的边接口"上，不是写在代码里** | 同上：花园只能next to墙 → *"除非围出一块完全封闭的区域，花园根本没地方放，规则就是这么造出来的"* | 💡 **"每一类都有自己的规则"应落成边相容性约束**，而不是一堆 if-else。且作者警告：*"这种规则写法能玩出的花样有限"* |

### 2.5 作者对"规则可读性"的设计取舍（值得照抄）

> *"我希望大形状**非常可预测**，小形状**允许随机变化**。所以只要围出封闭区域，就一定会有花园；但花园里那些小石墙可以完全不同。"*
> *"我想要的是：**用户觉得自己掌控着大形状，而我得以在小形状上捣鼓各种花样。**"*

还有更高优先级的 **recipes**（ Como花园、阶梯、雕像等隐藏样式），优先级高 → **稳定可复现** → 玩家可以主动再建出来。

> 📌 **这条应直接写进本项目的做 fa**：玩家不能感觉"形态是随机的"。**触发条件确定 → 大形态确定 → 细节可随机。**

### 2.6 🆕 存档格式反推揭示的数据模型（v0.3）

> 来源：B 组（townsclipper + Wolfram 对照实验）。**这是本项目唯一一批"从产物倒推实现"的硬证据**，与 §2.1 其余来源（访谈 / 讲座 / 复刻）性质不同——它是可以自己跑一遍验证的。

**数据模型（townsclipper 解码结果）**

```
世界   = corner 的稀疏集合                # 不是三维体素场
corner = { x, y, voxels: [type, ...] }    # 每个角点挂"一列" voxel，自下而上
type   : 0..14 = 15 种颜色；15 = ground
存储   : x 存 delta，y 存 offset；只存"放了块的" corner
```

> 💡 **最关键的一条**：它的世界模型是 **2D 角点 + 每角一列高度**，**不是** `Dictionary[Vector3i, ...]` 那种三维格子字典。§1 我们现值用的是后者——**两者不是同一类数据结构**，抄机制时不能直接照搬存档格式。

**推论：网格本身是 seed 的确定性产物**（🟡 中，**未获作者确认**）

Wolfram 那篇做了对照实验：截图做图像分析反推渲染网格坐标，拿 `.scape` 存档当 ground truth，**发现二者不是线性 / 分式变换关系**。作者自己的猜测是：

> *"我猜存档里存的是网格松弛算法的**初始种子**……不知道算法我就卡住了。"*

⚠️ 这是**第三方单源的 educated guess，不是作者原话**。旁证是：分享码只有几十个字符却能还原整座城 → 网格必然由短种子确定性展开。

**对 §5.5 的意义（工程侧推论，🔴 自设）**

若成立，Townscaper 的"生成"是**分两层**的：

| 层 | 机制 | 是否需 WFC |
|---|---|---|
| 网格 / 地形 | seed → 确定性松弛展开 | ❌ 不需要 |
| 瓦片选排 + 装饰 | WFC 约束求解 | ✅ 需要 |

→ 与 §5.5「先确定性查表、只在必要时上受限 WFC」方向一致，且给出更细的切分：**"要不要 WFC"不必全局回答，按层回答**。

🔴 **不得据此下结论**：「网格确定性」是 🟡 单源推测。要拿它当设计依据，须先复跑 townsclipper 或抓到作者关于 seed 的原话 → 已列入待办 **T-5**。

### 2.7 🆕 逐层判定：几何到底是不是"运行时程序生成"（v0.3）

> 起因：Benja 提问——"它的建筑是不是 **PCG** 实时生成 3D 网格 + 实时程序渲染？"
> 📌 **用语已规范**：程序化生成一律写 **PCG**（Procedural Content Generation）。**PGC 是另一个词**（Professionally Generated Content，与 UGC 相对），**不得用来指代程序化生成** —— 详见 §9。本行原文写作 PGC，v0.3 已改正。
> ⚠️ **这与 v0.1 的错误（§2.3）是同一个坑的两次发作**，只是从相反方向提出来。结论一致：**不是**。但"哪些层是、哪些层不是"此前没有逐层拆开，是本次才补的。

**决定性引述（作者本人，MCV/DEVELOP）**
> *"它（网格）在很多地方都奇怪而不规则，**但它是四边形构成的**。这意味着**我做内容时，我先做出方形瓦片，然后做出方形的拼图块，再把它们稍微扭一下去贴合**。"*
> *"基于瓦片的流程有个很大的好处：你做出的这些小拼图块**全是标准化的**，所以它们能互相拼上。当然，缺点是容易太重复——**网格的有机性带来的大形状，正好打破这种重复**。"*

**逐层判定**

| 层 | 是否运行时从零生成 | 依据 |
|---|---|---|
| **不规则网格** | ✅ **是** | 作者自述：六边形→三角→删边并四边形→细分→松弛 |
| **建筑几何构件** | ❌ **否，手工建模** | 作者原话「我做内容时……做出方形的拼图块」；C′ 组给出 51 构型 / 18 mesh（§2.2） |
| **构件选排** | ❌ 不涉及几何 | WFC 只决定"放哪一块"，不产生顶点 |
| **贴合 / 扭曲** | ⚠️ **运行时改顶点，但输入是 authored mesh** | C′ 组：*"每个 Cube 区块的模型根据当前网格的形状做扭曲"*；sketchpunklabs 复刻中的 **trilinear interpolation（把 cube tile 贴到不规则格子）** |
| **海浪 / 沙滩** | ✅ **是** | C′ 组：*"生成结束后根据生成轮廓线，再平滑，组合生成沙滩 mesh，再外扩成海浪 mesh"* |
| **庭院** | ⚠️ 二次 WFC（2D 版），**构件仍是 authored** | C′ 组：封闭空间内再跑一次 WFC，模型换成庭院围墙组 |

**关于"实时程序渲染"——这条部分成立**

渲染侧确实有自定义实时方案（🟡 C′ 组 / 🟢 Domestika 作者自述）：**分层写 RT 记录空间信息，偏移采样取色**取得环境光与遮蔽；作者自述是"放一张与建筑同形状的三维贴图，加一点 blur"。
→ 但这是**着色（shading）**，不是**几何生成（geometry）**。**"实时"是真的，"生成网格"不是。**

**为什么这个错觉特别强（值得记一笔）**

运行时确实在动顶点（贴合层），而且网格本身确实是算出来的——两者叠加，看起来就像"整个模型是实时生成的"。但**顶点的来源是人建的 mesh，算法只负责选和扭**。
> 📌 **判别口径**：问的不是"有没有运行时计算"，而是"**几何的 authorship 在谁手里**"。Townscaper 的建筑几何 authorship 在作者手里，算法只拿走了**选排权**和**形变权**。

## 3. 症结重述（v0.2）

```
现状：kind ─────────────────────► 固定 GLB（形态在出资产时就死了）
目标：kind + 邻居 ──► 选/拼一套部件（形态在放置那一刻决定）
                        ↑
               这一步 Townscaper 用 WFC，我们可以用更便宜的东西
```

**为什么"继续做资产"走不通（结论不变，理由更清楚了）**：一件墙类覆盖「4 朝向 × 直/转角/三岔/十字 × 有顶无顶 × 叠加态」就是数十件；而 `santorini-spec.md` §3.2 已把**单地点新增 10 件定标 ≤1,250 面**（v1.0 必做五件），**单件上限 ≤600**。**件数与面数都装不下**。

**Townscaper 用两招绕开，我们两招都能用**：

| 招 | Townscaper | 本项目可用性 |
|---|---|---|
| **形变复用** | 一个件 skew 去贴不同格子 | 🟡 **部分可用**：我们是规则网格，本来就不需要贴合。但"**同一个模型件在不同朝向/拉伸下复用**"仍省事 |
| **算法选排** | WFC | 🟡 **有条件可用**：见 §5.5 |
| **标准接口** | "所有拼图块都标准化，所以能互相拼接" | 🟢 **完全可用，且这是最该抄的一条** |

> 💡 **真正该抄的不是 WFC，是"拼图块全部标准化、所以能互相拼接、严丝合缝"这句话。** 有了标准接口，穷举组合就退化成"选哪几块"——这正是 v0.1 推荐的路线 C，只是现在我们知道它**有出处**了。

## 4. 分层设计改动（L0 → L5）

> 本节相对 v0.1 基本不变，改动已核实。

### L0 · 邻域签名（Neighborhood Signature）— 必做，全部改动的底座

```
signature = {
  up / down        : kind | empty
  n / e / s / w    : { kind, top_delta, same_class }   # top_delta = 顶面高差
  diagonal_mask    : 8 位                              # 转角判形用
  support_distance : int                               # 到最近支撑面的垂直距离
  exposed_edge_mask: 位掩码                            # 临空边
}
```

- **吸收现有唯一一处邻接逻辑**：`build_world.gd:173-186` 改消费 signature（**唯一源纪律**：邻接语义只在一处定义）
- **必须配套脏格局部重算**；若将来引入 WFC，这一层就是它的传播边界

### L1 · 把 `category` 从"UI 分页字段"升级为"行为契约"

| 新字段 | 作用 |
|---|---|
| `class` | `wall` / `roof` / `deck` / `connector` / `prop` / `terrain` |
| `snap` | 允许吸附方向 + 优先级 |
| `extends` | 能否延伸：放置时是否改写邻居形态 |
| `supports` | 能否被下接 |
| `hang` | 是否自动生成下接柱 |
| **edges** 🆕 | **四个边的接口标签**（如 `smooth` / `open` / `cap`）→ 直接对应 §2.4 第 4 条：规则写在边接口上 |

**代码改动**：`can_place()` 委托给 class rule。
⚠️ **破坏性改动（已核实）**：`can_place` 现被三处调用需同步——`main.gd:117`（ghost 合法性）、`world_model.place()`、`load_document()` 存档校验。

### L2 · 变体解析
`kind + signature → variant_id → 部件组合`。解析器必须是**纯函数**（同输入必同输出）→ 可单测、可缓存。

### L3 · 各类规则的展现形式

| class | 规则特征 | 展现形式 |
|---|---|---|
| `terrain` | 不做邻域形变，只做面剔除 | cube 合批（不变） |
| `wall` | 按四邻 + 高差判形；临空边加檐口/压顶 | 墙片 + 角件 + 檐口 |
| `roof` | 只能 `snap: down`；按被围边数判坡向 | 坡面 + 脊 + 山墙 |
| `deck` | 水平延伸，临空侧加栏杆；悬空触发 `hang` | 板 + 栏杆 + 桩柱 |
| `connector` | 主动连接两侧，自动补齐高差 | 台阶 / 坡道 / 阶梯件 |
| `prop` | 不做形变，可被 `supports` 引用 | GLB 实例化（不变） |

### L4 · 数据与存档
- `palette.json` 扩字段
- schema **1 → 2**
- 🔴 **建议：变体不进存档**（工程自设）。变体是**派生数据**，存档只记"玩家做了什么"，形态由规则重算 → **规则迭代不破坏旧档**
- `load_document()` 需兼容读 v1（现值：`schema_version != 1` **直接拒绝**，`world_model.gd:229`）

### L5 · 性能
- 非 cube 类**每件一个 Node3D + 独立 draw call**（`_add_prop`）→ 必做**按 variant_id 合批**
- **必做脏格局部重算**替代全量 `rebuild()`

## 5. 四类衔接的专门处理

### 5.1 弥缝 — 两种语义（+ v0.2 修正）

| 语义 | 含义 | 解法 |
|---|---|---|
| **① 几何弥缝**（视觉） | 露缝 / 穿插 / z-fighting | **部件自带搭接余量**（向邻向多出 0.02–0.05），**不要**严丝合缝 |
| **② 空缺弥缝**（功能） | 高度差、断口、悬空缺口补齐 | filler 件 |

> ⚠️ **v0.1 建议改写**：v0.1 建议把塞舌尔**楔石升格为跨地点通用 filler**。本地核实后发现**不建议照做**——
> `seychelles-spec.md:151` 楔石是**玩法核心件**（「垫」动词本体，每块 +1 格接触面）；`:209` 明确**"仅可置于石缝 / 石顶语义位"**。它是绑定堆叠平衡玩法的，**直接抽出来当通用 filler 会让"垫"这个动词失去载体**。
>
> ✅ **改建议**：不要搬楔石这个**件**，要搬它背后的**"语义位"概念**——本项目已经有了槽位语义的种子，把它提炼成通用的 `slot` 机制即可。
>
> 📌 楔石面数见 `quanzhou-seychelles-art.md` §9.3（SY-D-9，v1.4 补报）——**本文件不抄数值，只回源**。

### 5.2 转角（不同角度）

| 档位 | 代价 |
|---|---|
| **90° 四向**（沿用现状） | 最小，与现有 `rot` 4 档直接兼容 |
| **45° 八向** | 角件翻倍 + 需斜接件；`rot` 需扩到 8 档 |
| **自由角度** | ❌ 与体素网格 + 存档 schema 根本冲突 |

> **工程侧倾向（自设）**：锁 **90°**，45° 视余量。**注意：Townscaper 的不规则网格正是为了打破"方正重复"（见 §3 引述）——我们若锁 90°，失去的正是那份"有机感"**，要靠堆高起伏与颜色噪声去补。这条取舍要 Benja 拍（Q-2）。

### 5.3 叠加 — 缺的是"顶面接口契约"
- 现状支持**同 kind 堆叠**（cottage / barrel）
- 缺**跨类叠加**（屋顶压墙、露台压墙）→ 需**顶面接口契约**：墙类声明提供 `cap` 槽位（平 / 双坡 / 四坡），上层件声明 `occupies_cap`
- ⚠️ `item_height` 现在只有**整数高度**，没有顶面形制信息 → 必须扩

### 5.4 下接 — 归锚固判定 + 🔴 注意作者承认的雷
- 机制：`hang` 规则向下找最近支撑面，生成 N 段柱；找不到 → 放置非法或限制悬挑长度
- 🔴 **作者明确说过：支撑/细长构件是 WFC 最容易失败的地方**（§2.4）。所以下接**必须有显式兜底**，且兜底行为要进 UI 反馈（为什么放不下），不能静默
- 必须与 `location-gameplay-design.md` 的**圣托里尼 BFS 锚固 / 悬挑 3 格**、**塞舌尔接触面吸附****共用一套 anchoring 模块**

### 5.5 🆕 分叉：确定性查表 还是 WFC？

这是 v0.1 **完全没有识别出来的决策点**。

| | **确定性查表**（推荐先走） | **WFC 求解** |
|---|---|---|
| 形态来源 | `signature → variant` 纯函数，一次算出 | 约束传播 + 坍缩，多轮迭代 |
| 成本 | O(邻居数)，局部 | **随连通域增长**（§2.4） |
| 多样性 | 同一签名永远同一形态 | 同一处境可有多解，随机取 |
| gap-free 保证 | **靠人工保证覆盖所有 case** | 算法保证；但**可能失败** |
| 失败时 | 落到默认态（可控） | **静默失败 → 悬空残件**（作者承认） |
| 适用 | 规则是先验的、有限的 | 需要长程约束（如"围合才有花园"） |

> **工程侧建议（自设，须拍板）**：**先全用确定性查表**，只有出现"同一处允许多个解且不破坏观感"的需求时，才在**单个 class 内部**做**受限 WFC**（候选集 ≤ 8，传播半径 ≤ 2 格，失败回落到默认变体）。**不要一上来就全局 WFC** —— 那是 Townscaper 为了它那套视觉表现必须付的代价，我们不一定要付。

### 5.6 🆕 衔接件：纯 authored 还是半 PCG（v0.3）

> 起因：Benja 追问"用 **PCG** 实时生成 mesh 会不会更灵活"。→ **决策点 Q-7（§8）**

#### 先拆"灵活"——六种含义指向相反的答案

> 🔴 **以下六维拆分是工程自设，不是来源**；用于把"灵活"这个歧义词切可判定。

| 灵活性的含义 | PCG 实时生成 | 预制件 + 选排 |
|---|---|---|
| 少做资产 · 覆盖组合 | 🟢 组合数免费 | 🔴 件数会爆炸 |
| 贴合不规则地形 | 🟢 天然贴合 | 🟡 需额外形变件 |
| 美术形制可控 | 🔴 形制难把控 | 🟢 形制精确 |
| 迭代与调试可见 | 🔴 改代码不可见 | 🟢 所见即所得 |
| 运行时性能 · Web 端 | 🔴 重建更贵 | 🟢 缓存友好 |
| 玩法语义稳定 | 🔴 形态会漂移 | 🟢 动词有载体 |

**→ PCG 只在头两项赢。** 所以"更灵活"这句话**不加限定就是错的**。

#### 本项目特有的两条约束（Townscaper 没有，故不能照抄它的结论）

1. **纯色 flat shading、无贴图 → 形制是唯一的辨识手段**。Townscaper 只有一种北欧渔村风格，形制糊了也无所谓；**本项目要区分四个地点**，形制糊掉 = 核心卖点直接受损。若四个地点各要一套 PCG，等于**写四套生成器**，"省事"变成负担。
2. **WebGL2 / Compatibility 无 compute** → 生成只能走 CPU 的 GDScript 逐顶点循环；而 **rebuild 全量重建已是确认的真瓶颈**（满格粗估 100–300ms）。**PCG 会加重它，不是缓解它。**

> 📌 **别忘我们已经在路上**：`block_relief.gd` 的顶面连续噪声 + 塌落**就是运行时顶点生成**。分叉不是"要不要 PCG"，而是**扩到哪一层停**。

#### 建议：分层，别二选一（🔴 自设）

| 层 | 建议 | 理由 |
|---|---|---|
| 地形 / 土方 | **继续 PCG**，可扩 | 已落地，形制要求低 |
| **弥缝 / 衔接件** | **半 PCG**：authored 件 + 参数化拉伸 | ⭐ **性价比最高的一段**：台阶按高差拉伸、墙按长度拉伸——**一件顶几十种组合，且不必写生成器** |
| 建筑主体构件 | **保持 authored** | 四地点辨识度的载体 + 「垫」这类动词的载体 |
| 装饰 | **authored** | — |

> 🔑 **"半 PCG" 的判别口径**（与 §2.7 同一条）：**几何的 authorship 仍在人手里，算法只拿走"尺度权"。** 一旦算法拿走**形制权**，就滑向全 PCG —— 那条线就是分层停在哪里的界碑。

#### 排期影响（🔴 全部工程自设估算，未实测）

| 项 | 半 PCG | 纯 authored |
|---|---|---|
| **L2**（现 6–10 人日） | **+2–4**（加参数化维度 + 解析器支持拉伸） | **+6–12**（逐组合出件 + 资产返工） |
| **`block_relief.gd`** | 不受影响（地形层已在 PCG 侧）；但衔接件若也走 PCG，需**共用同一套噪声/塌落参数入口** → **+1–2** 做参数归口 | 不受影响 |
| **L5 变体合批**（现 2–4） | ⚠️ 同一件出现连续尺度 → **按 variant_id 合批失效**，须改按「件 id + 分档尺度」合批 → **+1–3** | 不受影响 |
| **Q-11 面数解禁** | 「PCG 省资产」在**面数**维度被削弱（硬顶已解除），**工时**维度仍在 | 同左 |

⚠️ 以上均为估算，**不构成判据**，不并入任何冻结数字（地板 74 / 推荐 ~81 / 满配 81–108）。

## 9. 纪律声明

- 本文件**不写入验收判据**，不含通过/阻断语义
- 数值全部标注来源；**工程自设的已在 §7 显式标注**
- 地点数值**只做回源指路，不存副本**（唯一源 = `water-lighting-params.md` v4.3）
- **作废内容留档不删**：§2.3 保留 v0.1 错误论断原文，标「已作废 · 勿用 · 勿删」
- 第三方重实现（andersource / sketchpunklabs / OrganicQuadGrid / quadrangulation）**不得当作作者原话引用**（§2.1 C 组）
- ⛔ **AI 生成的合成条目（Grokipedia 等）与内容农场转载一律不得作为来源**（§2.1 D 组）——它们的技术描述**看起来可信**正是其危险之处
- 来源引用须带**置信度**；🟠 / 🟡 来源**不得单独支撑设计结论**，须与 🟢 来源互证或显式标注为推测（§2.6 即按此处理）

### 用语规范（v0.3 立）

| 缩写 | 全称 | 含义 | 本项目用法 |
|---|---|---|---|
| **PCG** | **Procedural Content Generation** | **程序化内容生成** | ✅ **唯一正确写法**。指"用算法生成内容" |
| ~~PGC~~ | Professionally Generated Content | **专业生产内容**（与 UGC 相对） | ⛔ **禁用于指代程序化生成** |
| UGC | User Generated Content | 用户生成内容 | 正常语义使用 |

> 🔴 **PGC 不是 PCG 的笔误，是两个不同的词**——PGC 出自内容产业的 UGC / PGC / OGC 三分法，跟"程序化"毫无关系。**写成 PGC 会让读者误以为在谈内容来源（专业产 vs 用户产），而不是生成方式。**
>
> 来源：Shaker et al. 2016 对 PCG 的定义（*"algorithmic creation of game content with limited or indirect user input"*）；学术与行业文献（如 Sage《The artist and the automaton in digital game production》）一律用 PCG。
>
> 📌 本文件 §2.7 引述原写作 PGC，**v0.3 已改正**；其余章节一律用 PCG。**发现 PGC 一律改，不必保留沿革**（这是笔误级纠错，不是作废内容）。

# Godot 4 Web 效果实现与性能评估 · 降级方案

> 版本 v1.0 ｜ 日期 2026-09-23
> 目标环境：Godot 4.4 Web / WebGL2 / **GL Compatibility** / **单线程**（`GODOT_THREADS_ENABLED = false`）

---

## 0. 一条影响架构的硬结论（先看这个）

**Web 版 `index.wasm` 已经是 43.6MB。** 六个地点意味着六套美术资产。

如果按「单一产品内置多地点」的形态把所有地点资产打进主包，包体会膨胀到 Web 端不可用的量级。

> ### ⚠️ 结论：地点资产必须支持「按需加载」
> 玩家进入某地点时才下载该地点的资产包（材质、建材模型、植物）。
> **这不只是优化，而是决定「内置多地点」形态在 Web 上是否成立的架构前提。**

建议实现：Godot 的 `PCK` 分包 + `ProjectSettings.load_resource_pack()` 运行时挂载，把每个地点导出为独立 `.pck`。

## 1. Compatibility Renderer 的能力边界（哪些做不了）

| 能力 | Compatibility 下 | 影响 | 替代方案 |
|---|---|---|---|
| `hint_depth_texture` 深度纹理 | ❌ 不支持 | 水深渐变不能靠深度图 | **用「到岛心距离」推导**（已在参数表采用） |
| SSR 屏幕空间反射 | ❌ 不支持 | 水面无实时倒影 | 用 sky reflection / 简化 cubemap / 纯色 fake |
| SDFGI / VoxelGI 全局光照 | ❌ 不支持 | 无间接光 | 靠 `ambient_light_energy` + 烘焙感配色模拟 |
| FogVolume 体积雾 | ❌ 受限 | 嵊泗/Ria 的浓雾 | `Environment.fog` 距离雾 + `fog_aerial_perspective` + shader 高度雾 fake |
| Tessellation 曲面细分 | ❌ 不支持 | 波浪起伏不能靠细分 | 顶点动画或法线扰动 |
| Compute Shader | ❌ 不支持 | 无法 GPU 批量计算 | 全部走 CPU 或 shader fragment |
| Glow 泛光 | ⚠️ 有限支持 | 日落金色光晕 | 可用，但 `glow_hdr_threshold` 需调高避免全屏发光 |

## 2. 性能预算（建议硬上限）

| 项 | 上限 | 说明 |
|---|---|---|
| 水面 shader 指令数 | **< 30 ALU** | 全屏像素，超标直接掉帧 |
| 水面纹理采样 | **≤ 3 次** | 法线图 + 噪声 + （可选）岸线遮罩 |
| Draw call | **≤ 200** | 建造游戏方块多，必须合批 |
| 投影光源 | **仅 1 盏** DirectionalLight3D | 暖光灯用**自发光材质**而非真实光源 |
| Shadow atlas | ≤ 2048 | 建议 1024 起步 |
| 单地点建材资产 | 建议 ≤ 20 种 | 超出会显著增加包体与内存 |

> ⭐ **暖光灯千万不要做成 OmniLight3D。** 上一份内容策略已确认「夜间暖光灯亮起」是全游戏最强画面，
> 若每个灯都是真实光源，几十盏灯会让 Web 端直接崩溃。正确做法：**自发光材质（emission）+ 可选低分辨率烘焙光**。
>
> > ### 📌 2026-09-24 追加：本段的前瞻判断已被证实（请后人读到这里时更新认知）
> > 本段写于 **9 月 23 日**，**当时我们没有看过任何一行源码**——它是仅凭 Godot Web 端渲染常识做出的**前瞻判断**，不是基于本工程事实的诊断。
> > 今天 `tech-feasibility.md` §2 对 `build_world.gd::_add_prop()`（L224–231）的字节码反汇编证实：**暖光灯确实是真实 `OmniLight3D`**，这个推断完全正确；
> > 并且暴露了一层当初没预料到的恶化——**地形是全岛合并的单 ArrayMesh，于是 per-mesh 的 8 盏上限变成「全岛共享 8 盏」**，比当初估计的更糟。
> > ⚠️ **请不要把这条读成"早有警告却被忽略 / 延期至今"**：时间顺序上，游戏本体建得比本文档更早，这条是**先有判断、后有证据**，不是"警告在前、忽视在后"。
> > ✅ 现行方案：**共享光斑贴片**（单 quad + 不受光材质 + MultiMesh，混合模式 `blend_mix`），按 **core 层建材改造**立项（四地点共用，非泉州地点级 hack）。详见 `location-gameplay-design.md` §5 R-4 与 §4.9.2 ⑦。

## 3. 各效果开销评估

| 效果 | 开销 | 风险 | 建议 |
|---|---|---|---|
| 水体深浅渐变（距离法） | 极低 | 无 | ✅ 放心做 |
| 波浪法线扰动 | 低-中 | 中等 | ✅ 做，但限制采样次数 |
| 岸线泡沫 | 中 | 中 | ⚠️ 需要岸线遮罩，建议用距离场而非检测 |
| 水面反射 | 高 | **高** | ⚠️ 先做 fake（固定天空色混合），性能有余力再考虑 cubemap |
| 高度雾 fake（shader） | 中 | 中 | ✅ 嵊泗/Ria 需要，建议做成 shader 参数 |
| 植物批量渲染 | 低（若用 MultiMesh） | 低 | ✅ **必须用 MultiMeshInstance3D** |
| 爬山虎蔓延生长 | 中 | 中 | ⚠️ **不要每帧生成实例**，用 shader 生长遮罩（UV 阈值动画） |
| 悬挑结构检测 | 低 | 低 | ✅ 纯逻辑，无渲染开销 |
| 昼夜光线插值 | 极低 | 低 | ✅ 纯参数插值 |

## 4. 三级降级方案

建议在 `ProjectSettings` 或代码里维护一个质量等级，运行时根据设备自动切换。

| 参数 | High（桌面独显） | Medium（集显/中端） | Low（移动/低端） |
|---|---|---|---|
| 水面波浪 | 动态法线 + 双层扰动 | 单层静态法线 | 关闭，仅顶点轻微起伏 |
| `wave_normal_strength` | 按参数表原值 | × 0.6 | 0 |
| 岸线泡沫 | on | on（宽度减半） | off |
| ~~`reflection_strength`~~ 🗑️ **作废**（字段 v1 已删） | — | — | — |
| 阴影 | 软阴影 2048 | 硬阴影 1024 | **off** |
| `shadow_blur` | 按参数表 | 固定 1.0 | — |
| 高度雾 fake | on | on | off（用纯距离雾） |
| 植物 | MultiMesh 全量 | MultiMesh，密度 ×0.7 | MultiMesh，密度 ×0.4 |
| Glow | on | on（强度减半） | off |
| 目标帧率 | 60 | 30-60 | 30 |

> 🗑️ **`reflection_strength` 已从降级表移除**：该字段 **v1 已删**（`water-lighting-params.md` §3.3）——
> 水是 `render_mode unshaded`，不参与光照与反射；且当前 `background_mode = BG_COLOR`、**没有天空可反射**。
> ⛔ 不要为它保留降级档位。🔴 留着它，等 v1.1 上 T2 天空时会被当成"本来就该有的参数"复活。

**自动降级检测**：启动时用 `OS.get_video_adapter_driver_info()` 读显卡信息粗判，再结合前 3 秒实测帧率微调。

## 5. 包体与加载优化（Web 端重中之重）

| 手段 | 收益 | 优先级 |
|---|---|---|
| **地点资产按需加载（.pck 分包）** | 决定多地点形态能否成立 | ⭐⭐⭐ |
| **Basis Universal 纹理压缩**（`.ktx2` / `.basis`） | 纹理体积降 60-80%，且跨平台解码 | ⭐⭐⭐ |
| 减少 shader 变体 | 缩短编译阻塞时间 | ⭐⭐ |
| 音频用 `.ogg`（Web 端比 `.wav` 小很多） | 体积 | ⭐⭐ |
| 植物/建材共用材质，只换贴图 | 减少 shader 数量 | ⭐ |

> ⚠️ **单线程模式下 shader 编译会阻塞主线程**，表现为切换地点时明显卡顿。
> 建议：进入地点前做一次 shader 预热（离屏渲染一帧），或显示加载提示。

---

## 6. 与既有风险的关联

- **R-4（WebGL2 性能）**：本文是其细化，核心缓解手段是「参数化 fake + 三级降级」。
- **R-1（松弛感被目标侵蚀）**：性能降级不应削减「日落光线」与「暖光灯」，这两项是氛围核心，优先保。
- **43.6MB 首屏加载**（此前标记为最大转化杀手）：多地点必须按需加载，否则会进一步恶化这个指标。

---

## 7. 建议的验证顺序

1. 先在**雾港本体**上把水面 shader 参数化 + 三级降级跑通（不改视觉）
2. 实测三级在目标设备上的帧率，确认预算成立
3. 做圣托里尼时**先只上材质与参数**，再上机制，便于定位性能问题
4. 地点分包加载单独做一个 spike 验证（这是架构风险最高的一项）

## §1 概念对齐：你说的 geo meta 已经存在了三分之二

| 你的概念 | 现存对应物 | 现状 | 回源 |
|---|---|---|---|
| geo meta（岛屿轮廓/岸线/海水/气候/背景） | **`LocationProfile`（.tres）**：水体/光线/雾/建材表/**地形参数** | 已规划，未见实现 | `location-gameplay-design.md` §1.3 表第 2 项 |
| 每个地方一套地质 | 四地的**地形形态 + 地质对立**描述（湾+屿+滩涂 / 阶梯陡崖 / 沙丘半岛 / 花岗岩岛+白沙滩；沉积 / 火山 / 冰碛 / 大陆碎片） | **文字已写好**，散在各 spec | `location-gameplay-design.md` §6 对照表（行「地形形态」「地质对立」） |
| 初始化生成地质地图 | **`terrain_generator.gd`**，每地点一份 | 已列「全新开发」；现有极简实现在 `world_model.gd:reset()` | `location-gameplay-design.md` §1.5 目录树；`engineering-eval-st-d2-fog.md` §维度 1 |
| 统一的结构方式 | **§1.4「手感必须四地点完全一致」七项**（相机/建造操作/UI/昼夜/存档 schema/撤销深度/进出路径） | 已定，但**只覆盖操作层，未覆盖构件的组织与理解方式** | `location-gameplay-design.md` §1.4 |

**结论：geo meta 应该扩充 `LocationProfile`，不是另起炉灶。** 否则会出现两套「地点参数」互相漂移——这正是本项目唯一源纪律最忌讳的形态（回源 MEMORY.md「唯一源纪律」）。

🔴 **唯一源纪律在 geo meta 上的具体落法**：`geo meta` **不存**光照/雾/水体的数值副本，只存**引用键**。这些数值的唯一源是 `water-lighting-params.md`（四地 × 昼/晨/夜/日落 × 雾档）。geo meta 里写 `lighting_ref: "QUANZHOU"` 就够了——一旦存副本，四态色值就会在两个地方各自漂移，而验收单 A-11（🔴 阻断，天空盒四态色值通道）会失去回源。

## §2 三条职责正交（这条最重要，也最容易做混）

```
geo meta        = 这个地方「是什么」      每地点一份    决定：长什么样、能长成什么样
通用建造语法     = 构件「怎么组织」        全局一份      决定：玩家的心智模型，跨地点不变
location_mechanic = 玩家「做什么动作」      每地点唯一一个  决定：玩法动词
```

| 线 | 管什么 | 不管什么 | 硬约束 |
|---|---|---|---|
| **geo meta** | 地形轮廓/岸线/水体/气候/背景自然界/**可用构件子集**/**白名单内的规则覆写** | 不定义动词、不定义格位与接口 | 不存光照数值副本（见 §1） |
| **通用建造语法** | 格位坐标、构件边接口（`edges`）、吸附与叠加、语义位（slot）、撤销单元、变体解析规则 | 不管具体构件长什么样 | 四地点**一行代码都不要改**（§1.4 精神延伸） |
| **location_mechanic** | 该地点的唯一动词：连（线）/ 凿·悬挑（向外）/ 照（面）/ 叠（向上） | 不碰地形与构件组织 | **每地点只允许一个**（§1.5 硬性） |

**为什么必须切开**：第 2 点要求「地方特色强」，第 3 点要求「跨地点统一」，这两股力天然对冲。不切开的话，实现时会出现两种典型翻车：
- 把特色全塞进 mechanic → 四地各写一套结构逻辑 → 通用语法名存实亡，玩家换地点就要重学（违背第 3 点）
- 把特色全塞进外观参数 → 四地玩法同质，「不是换皮」这条底线守不住（回源 §0「四个动词落在四个维度是结构性证据」）

**判据（建议，非自设结论）**：一条规则要么住在通用层（跨地点一致），要么**显式声明**为 geo meta 可覆写项。**不存在第三种归属**。

## §3 「乱搭也具有该地特色」：geo meta 必须有三层，不是一层

只换外观（材质/颜色/比例）**做不到**这条。玩家用同一套语法乱搭，如果四地只差配色，结果就是四张换皮图。

| 层 | 内容 | 举例（泉州） | 强度 |
|---|---|---|---|
| **L1 外观参数** | 材质、色值、比例、噪声 | 红砖/蚵壳厝色系、滩涂泥黄 | 弱（只做到「像照片」） |
| **L2 构件子集** | 这个地点**有哪些/没有哪些**构件 | 有「滩涂」「石桥」「蚝壳墙」；**没有**「沙丘草甸」「花岗岩巨石」 | 中（玩家可选的集合已经被地方限定） |
| **L3 规则覆写** | 白名单内的**规则参数**被地点改写 | 地形交融的过渡宽度、生长物的密度上限、人造物的最大悬挑 | **强（「乱搭也像」的真正来源）** |

**L3 必须有白名单 + 上限**（这是我强烈建议加的约束）：geo meta 可以「调参」，但**不能新增规则类型**。可覆写的字段做成一张显式清单（例如 ≤12 个），越界即报错。理由：一旦允许地点随意加规则类型，通用语法的可迁移性会在第四个地点上线时崩掉，而崩的方式是「玩家换个地点就不会玩了」——这直接命中第 3 点的反面。

**geo meta 草案字段**（供讨论，非定稿）：

| 字段 | 内容 | 备注 |
|---|---|---|
| `island_outline` | 岛屿轮廓生成参数（形状基元、曲率区间、噪声频率） | 驱动地形生成器 |
| `coast_structure` | 岸线结构（崖/滩/栈桥占比、曲折度区间） | 决定「能不能连」 |
| `land_distribution` | 陆岛分布（岛数区间、面积比、**海陆比区间**） | 第 5 点「按什么比例和个数造岛」落在这 |
| `shoreline_shapes` | 允许的岸线形态集合（溺谷 / 沙嘴 / 潟湖 / 峡湾…） | 「所造的岛能以什么样的轮廓被填满」 |
| `hydro` | 海水（双层水、深浅、透明度）、海浪（wave 三项）、潮汐 | 数值回源 `water-lighting-params.md`，此处只存引用 |
| `climate_ref` | 气候/雾档/风的**引用键** | 🔴 不存副本 |
| `backdrop` | 背景自然界（远景、天空、生物、季节彩蛋） | 天空色值同样回源 |
| `palette_subset` | 可用构件 id 列表 + 三层归属 | 见 §5 |
| `rule_overrides` | 白名单内的规则参数覆写（≤12 项） | 见上 |

## §4 第 5 点：与 Townscaper 的取舍冲突，与 M1 验收项相撞

### 4.1 先精确化 Townscaper 到底做了什么

作者 Stålberg 的网格是**开局一次性生成、之后玩家不可改**（六边形内生成三角形 → 随机删边凑四边形 → 细分 → 几轮松弛）。就「开局定形、之后只在其上建造」这一点，**你的第 5 点与它方向一致**。

但作者同时有一条明确的设计取舍（他的原话大意）：

> **大形状要非常可预测，小形状允许随机变化——玩家必须感到自己掌控大形态。**

🔴 **冲突点**：「每次初始化都新生成一份地质地图」= 把**最大的那个大形状**随机化了。这正是作者刻意不让随机碰的东西。

### 4.2 与验收单的直接碰撞

M1 · 地形与视听成型（🔴 阻断项）要求：**「地形生成器完成……缩略图尺寸下能一眼认出是这个地方」**（回源 `acceptance-checklist.md` M1 门槛原文）。

如果地质地图是自由随机生成的，**它有可能生成不出该地点的辨识特征**（泉州的「湾+屿+滩涂」、圣的「新月崖」、CC 的「沙丘半岛」、塞的「环礁潟湖」）→ **生成器自己把 M1 打挂**。这不是理论风险，是自由噪声的必然：噪声不会保证产出「湾+屿+滩涂」三件套。

### 4.3 建议：受限生成 + 种子可见可重摇

1. **生成器输出的是「该地点地形形态的一个实例」，不是「任意地形」。** 即 geo meta 里写死**硬约束**：泉州必须产出 ≥1 个湾、≥N 个屿、滩涂占比落在区间内；圣的崖线必须连续且呈新月；塞必须产出中央潟湖。约束不满足 → **重摇**，不允许把不合格的地图交给玩家。
2. ~~**种子可见、可重摇、可锁定**：开局给玩家 3–5 张候选缩略图任选（或一键重摇），选定后本次存档固定。~~
   🔴 **Q-8 拍板（2026-10-07）**：**不设玩家选择**（Benja：「不要让玩家选，那样就少了探索乐趣」）。
   → 修订口径：**随机度拉满，重摇是系统的内部行为**——生成器按 geo meta 硬约束反复重摇，**直到产出合格地图才交给玩家，玩家全程看不到「选」这一步**。
   → 这样同时拿到三件事：探索乐趣（每次开局都未知）+ M1「一眼认出」（硬约束保底）+ 不违背「玩家掌控大形态」（掌控的是**造什么**，不是**地形长什么样**）。
   → 存档仍须记 `seed`（现 schema v1 已有该字段），保证「同一张图可复现 / 分享」；**重摇按钮只对新开局生效，不动已有存档**（见 R-F）。
3. **玩家的造岛范围由 geo meta 给定区间**（海陆比、岛数、可填轮廓），玩家在区间内自由——这才是「轮廓一开始定了、玩家按喜好填」的正确落法。

### 4.4 顺带的好消息：不是从零写生成器

`world_model.gd:reset()` 已经在做这件事的**极简版**：`FastNoiseLite`（seed 240910）+ 三个椭圆距离场 + 高度 0/1/2 + stone/grass/wood 分层 + `_seed_village()`。它是**地点无关**的（同一套椭圆给所有地点）。

所以第 5 点的真实增量是：**把 reset() 参数化成 geo meta 驱动**，而不是新写一个地形生成器。已列入排期的 `terrain_generator.gd`（每地点一份）正好承接。**注意不要重复记账**——见 §7。

## §5 第 6 点：三类构件的延展性 —— 顺带把 Q-1 结了

### 5.1 你的三层和现有 palette 三分类几乎一一对应

| 你的层 | 现 palette `category` | 现有件 | 匹配度 |
|---|---|---|---|
| 基础地形 | `地形` | grass / stone / wood / brick | ✅ 直接对应 |
| 自然生长物 | `自然` | tree / flower / **lamp** | ⚠️ **lamp 是人造物，归错了** |
| 人造物 | `建筑` | cottage / roof / arch / glass / beacon / windmill / barrel | ✅ 直接对应 |

现 `category` **只用于 UI 分页、不参与任何逻辑**（`main.gd:396-401`）。

**→ Q-1（分类口径）建议就此结案**：采用你的三层语义作为**行为类**（terrain / growth / built），UI 仍可按展示分组，两层并存。附带一条具体修正：**`lamp` 从「自然」重归档到「建筑」**（它是人造灯具，且是夜间玩法的关键件，归错会影响后续的规则归属）。

### 5.2 三层各自的延展规则（这是你第 6 点里最有价值的部分）

| 层 | 参考 | 在本项目怎么落 | 成本 | 备注 |
|---|---|---|---|---|
| **地形** | 文明地图编辑器的地形瓦片交融 | 邻域签名 → 选交融变体（与 `build-system-classes.md` v0.2 同一套机制） | 中 | 地形件都是 cube 且已合并 ArrayMesh，比建筑件便宜 |
| **生长物** | 植物真实习性（丛生/蔓延/附生/独生） | **最小构件不必是单株**——按「个体大小比例的适当性」定；系统按邻域/密度自动聚成丛 | 中 | 见 5.3 |
| **人造物** | 帝国时代 / 部落冲突的建材拼接 | 边接口相容 + 经济性约束（不悬空、跨度有上限） | 高 | 这一层是 Townscaper 式衔接自动化的主场，也是最需要**确定性查表**的一层（Q-6） |

### 5.3 生长物那条要特别处理：形态是「解析出来的」，不是「玩家摆的」

你说「最小构件不一定是单株单只」——**这条我完全赞同，而且它恰好和本项目最紧的约束同向**：

- **省面数**：一丛（1 件、≤600 面）比「多株各自摆放」省得多，直击 `santorini-spec.md` §3.2 的预算约束（本文件不抄数，只回源）
- **省 draw call**：丛生做成一件，MultiMesh 也更整齐

但带来一个**操作粒度问题**：玩家点一下，应该长出「一株」还是「一丛」？

**建议**：玩家放的是**个体**，系统按邻域与密度**自动聚成丛**（形态在解析期决定，不进存档）。这样：
- 玩家心智简单（我种了一棵树，旁边又种一棵 → 长成一片林）
- 与 Q-4「变体不进存档」是同一条原则，改规则不破坏旧档
- ⚠️ 需要定义 **撤销单元**：撤销一次应该消掉「个体」还是「整丛」？（建议：个体——玩家点了几下就撤几下）

## §6 三条现实约束（写在前面，免得方案做一半才发现）

### 6.1 面数硬顶**已解除**（Q-11，2026-10-07 拍板）

**拍板**：不设面数上限。原「全库硬顶 ≤600 / 单件预算」的口径**不再作为约束**。

**核实到的现值**（本轮实测，不是估算）：

| 事实 | 值 | 来源 |
|---|---|---|
| 现役 9 件 GLB 实测三角面合计 | **2,722** | 逐个解析 GLB accessors 实测 |
| 其中 `barrel` | **632** — **已超过原「全库硬顶 ≤600」** | `project/assets/models/manifest.json` + GLB 实测一致 |
| 其余 8 件 | 44–560（roof 44 / tree 72 / lamp 134 / arch 208 / cottage 272 / windmill 276 / beacon 524 / flower 560） | 同上 |

→ **「实现已经突破了面数预算」成立**：不是规划上的松动，是**现役资产里就已经有一件超标**（barrel 632）。另 `3D tools config/prompt-library.md` 记有「海椰子面数已破例（Benja 2026-09-25）」的先例。所以本次拍板是**追认现状 + 放开**，不是凭空放宽。

**约束接棒给谁（Q-11 之后真正要守的东西）**：

| 接棒约束 | 现行口径 | 来源标注 |
|---|---|---|
| **Draw call ≤ 200** | 建造游戏方块多，必须合批 | 回源 `godot-web-perf.md` §2「性能预算（建议硬上限）」｜来源 = **工程**（tech-feasibility 系） |
| 水面 shader < 30 ALU / 采样 ≤3 次 | 全屏像素，超标直接掉帧 | 同上 |
| 目标帧率 60 / 30–60 / 30（三级降级） | 切片阶段实测 | 同上 §7 |
| 顶点总量 / 几何数据化体积 / 内存 | **尚无现成口径** | 🔴 **工程自设待拟**，须 Benja 拍板 |

⚠️ **面数解禁不等于没有约束**：面数升上去，最先撞线的是**全岛合并 ArrayMesh 的顶点总量**与 `rebuild()` 全量重建的耗时（见 R-D），以及 Web 首屏的几何数据体积。**建议在切片阶段先拟一份运行时预算**（顶点总量 / 单帧重建耗时上限 / 资产总体积），替代原来的面数预算 —— 这件事不做，等于把一个显性约束换成了一个没人看的隐性约束。

💡 交融方案因此**回到可选**：几何变体现在不再是禁区。但**仍建议「顶点色过渡为主 + 几何变体只做关键形」**——理由不再是面数，而是**变体数量会直接推高顶点总量与重建耗时**。

### 6.2 Web 端：全岛单 ArrayMesh 的老问题会变重

现状：地形是**全岛合并的单 ArrayMesh**，约 12,000 方块，`rebuild()` **全量重建**（回源 `engineering-eval-st-d2-fog.md` §维度 1/4）。

地形变体化 + 生长物聚丛 → 顶点数上升、重建成本上升。而放置是高频操作（每次放置都可能触发 rebuild）。**这是新增风险 R-D，需要在切片阶段实测，不能默认。**

### 6.3 存档：地形可再生成 = 必须存生成器版本

现 schema v1 已存 `seed` 与 `natural` 标记。若地形由生成器产出：

- 必须新增字段：**`geo_meta_version` + `generator_version`**（§1.4 第 5 条「存档 schema 只增字段不改结构」→ 可行）
- 否则将来生成器一改，**旧档重开地形就变样**——玩家的作品被系统改动，这是 P1/P2 直接受损的事故级问题
- 「重摇种子」如果允许对已存档使用，需要明确是否清空玩家作品（建议：**重摇 = 新档，不动旧档**）

### 12.1 被命中的判据

`3D tools config/README.md`（v1.2 草稿）把选型判据权重重置为：

|---|---|
| Tripo 因 `face_limit` 升为 B 路由主力 | **该理由消失**，B 路由主力需重新论证 |
| 混元 LowPoly「下限 3000 面 = 超预算 5–15 倍」 | **不再是缺点**（A 路由中式具名构件反而更可用） |
| Meshy / Rodin「无生成端面数参数」 | **不再是缺点** |
| Rodin 保持「评测保留、不划出」 | 不受影响（理由与面数无关） |
